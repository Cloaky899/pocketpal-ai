# In-App Renderer Feasibility Decision

## Decision

Use `manim-web` as the first local preview engine inside a bundled React Native WebView, behind a typed declarative visualization DSL and a strict message bridge. Retain the existing isolated Manim Community Edition renderer for high-fidelity Python/LaTeX/FFmpeg export and as a fallback when the in-app engine does not support a requested feature.

The app will not execute model-generated Python or JavaScript. The model will generate a versioned DSL document, the mobile compiler will validate it and produce an allowlisted engine bundle, and the WebView will execute only the bundled compiler/runtime path.

## Evidence collected

The candidate was inspected from the current `maloyan/manim-web` main snapshot at commit `5124d26`. Its package identifies as `manim-web` version `0.3.24`, is TypeScript-first, uses Three.js/WebGL, exposes a React integration at `manim-web/react`, and is licensed under MIT.[1]

The candidate’s local validation suite passed with npm because Corepack could not verify the sandbox’s current pnpm signing metadata. The successful gates were:

| Gate                           | Result                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript typecheck           | Passed                                                                                                                              |
| Unit tests                     | Passed                                                                                                                              |
| Production/browser build       | Passed                                                                                                                              |
| ESLint                         | Passed with existing advisory complexity/max-lines warnings and no errors                                                           |
| Focused browser example test   | Passed                                                                                                                              |
| Default integration smoke test | Failed because the repository Playwright config targets `/`, while the Vite workspace has no root `index.html` and returns HTTP 404 |

The focused browser test loaded `/examples/square_to_circle.html` through Vite, launched the installed Chromium binary, found a visible canvas with non-zero dimensions, and completed successfully. The default smoke-test failure is a harness configuration problem rather than an engine-render failure; the app’s CI should target an explicit local fixture entrypoint instead of assuming a root page.

## Runtime constraints

The engine’s browser renderer constructs a `THREE.WebGLRenderer` against an `HTMLElement`, creates or reuses an `HTMLCanvasElement`, depends on `window.devicePixelRatio`, and handles WebGL context loss/restoration. These requirements are compatible with a local WebView surface but are not compatible with direct execution in a normal React Native view without a browser-like DOM/WebGL host.[2]

The candidate has a public React integration built around `ManimScene`, `useScene`, `useAnimation`, and playback controls. Its scene object supports `play`, `pause`, `resume`, `stop`, `seek`, deterministic scene construction, and disposal. This is sufficient for an in-app preview adapter when the scene code is generated by a trusted compiler rather than injected as arbitrary source.[3]

The candidate also contains browser-oriented GIF/video export paths. Video export uses `HTMLCanvasElement.captureStream`, `MediaRecorder`, browser codec support, `requestAnimationFrame`, and DOM object URLs; GIF export uses browser canvas extraction and a worker path. These APIs are not a safe assumption for native iOS/Android release builds inside a WebView. Therefore, local in-app rendering is the first acceptance target, while MP4/WebM export remains delegated to the existing ManimCE renderer until a device-matrix export proof passes.[4]

## Required integration boundary

The mobile application will use the following boundary:

| Boundary                     | Design                                                                                                     |
| ---------------------------- | ---------------------------------------------------------------------------------------------------------- |
| Model → app                  | Structured `VisualizationProgram` DSL only                                                                 |
| App compiler → WebView       | Versioned, JSON-only `CompiledSceneBundle`; no raw code, imports, URLs, or dynamic evaluation              |
| WebView → app                | Typed protocol events with run ID, sequence number, stage, metrics, and bounded diagnostics                |
| App → high-fidelity renderer | Only validated programs after local technical/visual review, using the existing isolated renderer contract |

The WebView will be bundled locally, navigation will be restricted, external network access will be disabled wherever the platform allows it, and engine state will be disposed on cancellation, unmount, backgrounding, timeout, or WebGL context loss.

## Feasibility acceptance result

The feasibility gate passed for the following scope:

1. Local browser/WebView preview of supported 2D scenes is technically viable.
2. The engine provides enough scene lifecycle and playback controls for deterministic frame sampling.
3. React Native should host the engine through a local WebView bridge rather than attempting to run it directly in the native React tree.
4. A typed DSL is mandatory because the engine API accepts executable TypeScript callbacks.
5. Local video export is deferred until real Android and iOS release-mode tests prove codec and capture support.

The next implementation phase will add the shared DSL and deterministic compiler before adding the WebView dependency to the main application. The existing Python renderer remains unchanged during that phase.
